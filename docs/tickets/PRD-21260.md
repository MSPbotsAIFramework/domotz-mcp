Per the Domotz Public API's live OpenAPI definition (`GET https://api-us-east-1-cell-1.domotz.com/public-api/v1/meta/open-api-definition`, fetched 2026-10-30 — the repo's own README calls this "the documented endpoints" and this skill's design leg does not have a Domotz test account to hit it directly, so this is a documentation read, not a live call), the account-level alert surface today is:

  - `GET /alert-rule`, `POST /alert-rule`, `GET /alert-rule/{id}`, `PATCH /alert-rule/{id}` — Alert Rules (the current alert-configuration resource: datapoint, condition, severity, operands).

  - `POST`/`DELETE /alert-rule/{id}/agent/{agent_id}/device/{device_id}/binding` — attach/detach a rule to a device.
  - `POST`/`DELETE /alert-rule/{id}/contact-channel/{channel_id}/binding` — attach/detach a notification channel to a rule.

  None of these six endpoint groups have a tool today. `alert-profile` does not appear in the current OpenAPI definition as a named resource — Domotz's own release notes (searched 2026-10-30) describe Alert Rules as the current, actively-evolving alert-configuration surface, which suggests `alert-profile` is an older/parallel surface. This repo's two existing alert tools may therefore be calling a legacy path; see Risks.

## Product design

### Goals / Non-goals

**Goals**: give an agent the "manage alerts" half of the ticket that today's tools don't cover — see which alerts have fired, resolve one, see the account's Alert Rules, and attach/detach an existing Alert Rule to a collector or device.

**Non-goals** (see Open questions — non-blocking, proceeding on these assumptions):
- Authoring new Alert Rules (create/update: picking a datapoint, condition, severity, operands) is out of scope. That requires enumerating Domotz's datapoint catalog and condition operators, which the account-specific portal UI already does with guided pickers; getting this wrong from an API spec alone risks silently-wrong alert conditions. An agent can still attach an *existing* rule to new coverage (goal above).
- Attaching/detaching notification (contact) channels to a rule is out of scope — there is no tool today to list contact channels, so there is no way for an agent to discover a valid `channel_id` without adding a whole new resource area not requested by this ticket.
- No change to the already-covered capabilities (devices, inventory, topology, legacy alert-profile viewing).

### Acceptance criteria

- **AC1**: Given a valid API key and a required time window, when the agent calls the new "list fired alerts" tool, then it returns the account's alerts for that window (optionally narrowed by severity, status, alert rule, collector or device), paginated the same way as the repo's other list tools (`offset`/`has_more`/`next_offset`).
- **AC2**: Given a specific alert and `confirm: true` (set only after the user approved resolving that exact alert), when the agent calls the new "resolve alert" tool, then Domotz marks the alert resolved and the tool reports it was sent; given `confirm` is not `true`, the tool must not call Domotz and must say so, mirroring `domotz_power_outlet_control`'s existing confirm gate (`src/domotz_mcp/tools/power.py:38-69`).
- **AC3**: Given a valid API key, when the agent calls the new "list Alert Rules" tool (optionally the new "get one Alert Rule" tool with an id), then it returns the account's configured Alert Rules as Domotz returns them.
- **AC4**: Given an Alert Rule id and a collector (`agent_id`), the agent can attach that rule to the collector and remove the attachment, each gated the same way as AC2 (`confirm: true`, not sent otherwise).
- **AC5**: Given an Alert Rule id, a collector and a device, the agent can attach that rule to the device and remove the attachment, same confirm gate as AC4.
- **AC6**: Every new tool is listed in `tools/list` without credentials, follows the existing error envelope (`not_configured` / `unauthorized` / `not_found` / `invalid_argument` / `rate_limited` / `upstream_error`, `src/domotz_mcp/api_client.py:63-73`), and is reachable from `domotz_navigate("alerts")` / `domotz_back()`.
- **AC7 (regression)**: The already-covered capabilities (device monitoring, inventory, topology, the two existing alert tools) are unchanged in behavior and signature.

### Open questions

- **Scope of "manage alerts"** (non-blocking, proceeding on the stated assumption): the ticket is a one-liner with no specifics. Assumption: "manage" means operate on the account's existing alert surface (see what fired, resolve it, control which collectors/devices an existing rule applies to) — not author new alert conditions or wire up new notification channels, both of which are portal-UI tasks (see Non-goals). If the requester wants rule authoring, that is a follow-up ticket.
- **Uniform confirm-gating** (non-blocking): all five new write tools require `confirm: true`, matching the repo's one existing write precedent (`domotz_power_outlet_control`) even though resolving an alert is lower-stakes than cutting power to a device. Picking one consistent rule (every write action requires explicit, per-call confirmation) is simpler to review and keeps the safety bar the repo already set.
- **Legacy `alert-profile` endpoints** (non-blocking): `domotz_alerts_profiles_list` / `domotz_alerts_device_list` call `GET alert-profile...`, which the current public OpenAPI definition does not list as a named resource (see Current state). This design keeps both tools unchanged because there is no test account to confirm live behavior either way, and removing a listed tool would be a breaking change (`tests/test_contract_types.py:1-19` treats tool names and parameter types as a public contract) that this ticket's scope does not call for. If a later ticket's self-test or review finds `alert-profile` 404s in production, migrating those two tools onto the Alert Rule resource is a follow-up, not a must-fix here.

## Tech design

### Conclusion

Add six new read-only tools and update the two existing documentation/registration points, all inside the existing `alerts.py` module and the shared plumbing it already uses (no new dependency, no new module). One client method (`delete`) is added; every new call is a plain `GET`/`POST`/`DELETE` with no request body, so no JSON-body support is needed on the HTTP client.

### Where the current implementation lives

- Tool registration: `src/domotz_mcp/tools/alerts.py:24-45` (`register(mcp, client_factory)`, called from the tools package per `src/domotz_mcp/tools/__init__.py:14`).
- Shared argument types / error wrapper: `src/domotz_mcp/tools/_common.py` — `AgentId`/`DeviceId` (`:41-42`), `READ_ONLY`/`POWER_ACTION` annotations (`:32-35`), `window()` helper (`:95-110`), `run_tool()` (`:113-142`).
- HTTP client: `src/domotz_mcp/api_client.py` — `DomotzClient.get`/`post` (`:118-122`), the generic `request()` that already accepts any HTTP method (`:124-167`).
- Navigation / discovery: `src/domotz_mcp/tools/navigation.py` — `DOMAINS["alerts"]` (`:48`).
- Agent-facing usage text: `src/domotz_mcp/server.py` — `INSTRUCTIONS` (`:45-64`), alerts bullet at `:58-59`.

### Option analysis

- **Where to put the new tools** — chosen: extend `src/domotz_mcp/tools/alerts.py` in place. Alternative considered: a new `alert_rules.py` module. Rejected because the repo keeps one module per `DOMAINS` entry (`agents.py`, `devices.py`, `metrics.py`, `network.py`, `alerts.py`, `power.py`), and Alert Rules and fired Alerts are both part of the existing `"alerts"` domain in `domotz_navigate` — splitting them into a second module would not match that one-module-per-domain shape for no benefit.
- **How many tools** — chosen: six thin tools (`domotz_alerts_list`, `domotz_alerts_resolve`, `domotz_alert_rules_list`, `domotz_alert_rules_get`, `domotz_alert_rules_bind_agent`/`unbind_agent`, `domotz_alert_rules_bind_device`/`unbind_device` — eight total counting bind/unbind pairs separately). This matches the repo's existing granularity (21 thin tools today, one per Domotz endpoint, README.md "Delivery notes": "All tools always listed") rather than one tool with an `action` enum. A single parameterized tool would need a larger, harder-to-validate argument shape and would not match any existing tool in this repo.
- **Rule authoring (create/update)** — considered and rejected for this ticket; see Non-goals / Open questions above.

All eight new tools return a JSON string (pass-through of the Domotz response, or a small wrapper dict for the two bind/unbind pairs that otherwise return 204 with nothing to show), matching every existing tool's "errors come back as a JSON envelope instead of an exception" contract (`README.md:137-146`).

| `domotz_alerts_resolve` | `POST /alert/{alert_id}/resolve` | **alert_id**, **confirm** | `ALERT_ACTION` |

`domotz_alerts_resolve` and the four bind/unbind tools follow `domotz_power_outlet_control`'s exact confirm-gate shape (`src/domotz_mcp/tools/power.py:51-58`): without `confirm: true` they return `{"sent": false, "message": "Not sent. Ask the user to approve ..., then call again with confirm: true."}` and never call Domotz; with it, they call Domotz and return `{"sent": true, ...the relevant ids..., "note": "..."}`.

Error envelope (unchanged, `src/domotz_mcp/api_client.py:63-73` / `src/domotz_mcp/_json.py:177-178`): `{"error": {"code": "...", "message": "...", "retryable": bool}}`, `code` one of `not_configured`, `unauthorized`, `not_found`, `invalid_argument`, `rate_limited`, `upstream_error`.

Credentials: unchanged — `X-Domotz-API-Key` / `X-Domotz-Region` (`README.md:89-97`). No new header.

### Key flow / sequence

1. Agent calls `domotz_alerts_list(from_time, to_time, ...)` → sees which alerts fired, including `alert_rule_id` / `collector_id` / `device_id` on each.
2. Agent calls `domotz_alert_rules_get(alert_rule_id)` to see the rule's condition/severity if it needs to explain the alert to the user.
3. If the user asks to silence or resolve: `domotz_alerts_resolve(alert_id, confirm=true)` (after asking the user to approve the specific alert), or `domotz_alert_rules_unbind_device(...)` / `unbind_agent(...)` to stop the rule firing for that device/collector going forward.
4. If the user asks to extend monitoring: `domotz_alert_rules_list()` to find an existing rule, then `domotz_alert_rules_bind_device(...)` / `bind_agent(...)`.

### Non-functional

- **Idempotency / concurrency**: reads are naturally idempotent. The four bind/unbind actions are not guaranteed idempotent by Domotz (calling bind twice may 4xx on an already-bound pair); this is surfaced through the existing error envelope (`invalid_argument` or similar), the same way `domotz_power_outlet_control` already handles non-idempotent writes — no new handling needed.
- **Multi-tenant isolation**: unchanged. Every tool still takes the Domotz API key from the per-request header via `get_client_from_context()` (`src/domotz_mcp/server.py:67-72`); nothing is cached or shared across requests (`src/domotz_mcp/api_client.py:35-37` — the shared `httpx.AsyncClient` carries no credentials of its own).
- **Performance**: `GET /alert` is a list endpoint; it follows the same paging contract (`page_size`/`page_number`/`offset`/`has_more`/`next_offset`) as every other list tool via the existing `locate()`/`page_result()` helpers (`src/domotz_mcp/tools/_common.py:57-92`) — no new performance surface.
- **Security**: no new credential type; writes keep the same explicit `confirm: true` gate the repo already uses for `domotz_power_outlet_control`, so an agent cannot resolve an alert or change alert coverage without the human approving that specific action first.
- **Observability**: every new tool goes through the shared `run_tool()` wrapper (`src/domotz_mcp/tools/_common.py:113-142`), which already logs `tool=<name> outcome=... ms=...` for every call — no new logging code needed.

### Deviation from the tech design (and why)

- **`ALERT_ACTION.destructiveHint`**: implemented exactly as designed (`False`, unlike `POWER_ACTION`'s `True`) — correctly reflects that resolving an alert or (un)binding a rule never destroys data, unlike cutting power to equipment. This is a technical (non-user-visible) annotation value, so it was mine to adjust per the design/implementation split. It did surface one knock-on fix: the repo's existing generic test `test_annotations_match_side_effects` asserted `destructiveHint is (name in WRITE_TOOLS)` — a binary rule that was only ever exercised by one write tool (`domotz_power_outlet_control`, genuinely destructive) and does not hold once a *non*-destructive write tool exists. Split the existing `WRITE_TOOLS` set into `WRITE_TOOLS` (drives `readOnlyHint`) and a new `DESTRUCTIVE_TOOLS` (drives `destructiveHint`); `domotz_power_outlet_control` is the only member of the latter, so its existing behavior/test outcome is unchanged. This is covered by `test_annotations_match_side_effects`, now exercised for all 29 tools.
- **Test file placement**: the design's Test strategy section suggested all new tests would live in `test_tools.py` (mirroring an assumed `domotz_power_outlet_control` confirm test there). In this repo, mocked-HTTP behavior tests (confirm gates, path assertions, response shaping) actually live in `test_api_client.py` using its `Recorder`/`_call()` fixtures (e.g. `test_outlet_control_requires_confirm`); `test_tools.py` holds schema-level generic checks parametrized over `EXPECTED_TOOLS`. Followed the repo's actual convention instead of the design's assumption to avoid duplicating the mocking infrastructure in two files. `docs/tickets/PRD-21260.ac.json`'s `tests` fields were updated to point at the real locations.
- Everything else (tool names, parameters, endpoints, error envelope, annotations' `readOnlyHint`/`idempotentHint`/`openWorldHint`, confirm-gate response shape) matches the design as written.
